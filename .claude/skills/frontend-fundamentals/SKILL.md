# 코드 코어 원칙 (Code Core Principles)

이 skill은 프레임워크나 언어에 관계없이 모든 개발자가 따라야 할 근본적인 코드 품질 원칙을 제공합니다.

## 왜 이 원칙들이 중요한가

이 네 가지 원칙이 함께 작동하여 다음과 같은 코드를 만듭니다:
- **이해하기 쉬운** - 새로운 팀원도 코드가 무엇을 하는지 빠르게 파악할 수 있습니다
- **안전하게 변경 가능한** - 수정 사항이 예측 가능하고 국지적인 영향만 미칩니다
- **테스트하기 쉬운** - 각 부분을 독립적으로 테스트할 수 있습니다
- **확장 가능한** - 코드베이스가 유지보수 불가능해지지 않고 성장할 수 있습니다

## 네 가지 핵심 원칙

### 1. 응집도 (Cohesion)
**"관련된 것은 함께, 관련 없는 것은 따로"**

응집도가 높은 코드는 관련된 기능을 함께 그룹화하고 무관한 관심사는 분리합니다. 각 모듈은 하나의 명확한 목적을 가져야 합니다.

**상세 가이드:** [cohesion.md](docs/frontend-fundamentals/cohesion.md)

**다음 경우에 특히 유용:**
- 새로운 컴포넌트/모듈을 작성하는데 무엇을 함께 둬야 할지 모르겠을 때
- 함수/클래스가 너무 많은 관련 없는 일을 하고 있을 때
- 큰 모듈을 작은 모듈로 어떻게 나눌지 결정해야 할 때
- 코드가 여러 관련 없는 곳에 흩어져 있다고 느껴질 때

**핵심 개념:** 단일 책임(Single Responsibility), 관련 기능 그룹화, 일관된 추상화 레벨

### 2. 결합도 (Coupling)
**"추상화에 의존하고, 구현에 의존하지 말라"**

낮은 결합도는 모듈들이 서로에 대한 의존성이 최소화되었음을 의미합니다. 한 모듈의 변경이 다른 모듈의 변경을 거의 요구하지 않습니다.

**상세 가이드:** [coupling.md](docs/frontend-fundamentals/coupling.md)

**다음 경우에 특히 유용:**
- 모듈들이 너무 강하게 연결되어 있을 때
- 한 곳을 고치면 여러 곳이 깨질 때
- 테스트하려면 복잡한 의존성 설정이 필요할 때
- 구현체를 교체해야 할 때 (데이터베이스, API, 서비스 제공자 등)

**핵심 개념:** 의존성 역전(Dependency Inversion), 인터페이스 분리(Interface Segregation), 이벤트 기반 통신, 의존성 주입(Dependency Injection)

### 3. 가독성 (Readability)
**"코드가 말하는 것과 하는 것이 일치해야 한다"**

가독성 좋은 코드는 의도를 명확하게 표현합니다. 코드의 구조와 네이밍만으로도 동작이 명확해야 하며, 긴 설명이 필요 없어야 합니다.

**상세 가이드:** [readability.md](docs/frontend-fundamentals/readability.md)

**다음 경우에 특히 유용:**
- 코드를 깊이 분석하지 않으면 이해하기 어려울 때
- 변수/함수명이 의도를 명확히 드러내지 않을 때
- 깊은 중첩 때문에 코드 흐름을 따라가기 어려울 때
- 구현 세부사항이 비즈니스 로직을 가릴 때

**핵심 개념:** 관심사 분리(Separation of Concerns), 의도를 드러내는 이름, 불리언 명확성, 중첩 줄이기, 구현 세부사항 숨기기

### 4. 예측 가능성 (Predictability)
**"일관된 패턴, 기대되는 동작"**

예측 가능한 코드는 일관된 패턴을 따릅니다. 비슷한 작업은 같은 방식으로 동작하여 코드베이스를 직관적으로 탐색할 수 있게 합니다.

**상세 가이드:** [predictability.md](docs/frontend-fundamentals/predictability.md)

**다음 경우에 특히 유용:**
- 비슷한 함수들의 인터페이스나 동작이 일관성 없을 때
- 에러 처리가 코드베이스 전체에서 다를 때
- 함수가 숨겨진 부작용을 가지고 있을 때
- 상태 전환이 불명확하거나 복잡할 때
- 네이밍 컨벤션이 일관성 없을 때

**핵심 개념:** 일관된 시그니처, 명확한 부작용, 일관된 에러 처리, 명확한 상태 전이, 일관된 네이밍

## 이 Skill 사용하기

### 코드 작성 시
1. **계획 단계**: 응집도(무엇을 함께 둘까?)와 결합도(모듈이 어떻게 상호작용할까?) 고려
2. **구현 단계**: 가독성(명확한 의도)과 예측 가능성(일관된 패턴)에 집중
3. **리뷰 단계**: 네 가지 원칙을 체계적으로 체크

### 코드 리뷰 시
체크리스트 방식 사용:

**응집도 체크:**
- [ ] 이 모듈의 목적을 한 문장으로 설명할 수 있나?
- [ ] 관련 없는 기능들이 섞여 있지 않나?

**결합도 체크:**
- [ ] 구체 구현이 아닌 추상화에 의존하고 있나?
- [ ] 독립적으로 테스트/변경 가능한가?

**가독성 체크:**
- [ ] 이름과 구조만으로 의도가 즉시 명확한가?
- [ ] 코드가 위에서 아래로 자연스럽게 흐르는가?

**예측 가능성 체크:**
- [ ] 코드베이스의 다른 곳에서 사용된 패턴을 따르는가?
- [ ] 동작과 부작용이 명확하고 예상 가능한가?

### 리팩토링 시
1. 어떤 원칙이 가장 심하게 위반되었는지 파악
2. 해당 원칙의 레퍼런스를 읽고 상세 가이드 확인
3. 권장 패턴을 점진적으로 적용
4. 개선이 다른 원칙을 위반하지 않는지 검증

## Quick Reference: 일반적인 안티패턴

| 문제 | 위반된 원칙 | 조치 |
|------|-----------|------|
| 모든 걸 하는 God 컴포넌트/함수 | 응집도 | 책임별로 분리 |
| 의존성 때문에 테스트 어려움 | 결합도 | 인터페이스 도입 |
| 코드가 무엇을 하는지 불명확 | 가독성 | 네이밍 개선, 중첩 줄이기 |
| 같은 함수가 다르게 동작 | 예측 가능성 | 패턴 표준화 |
| 깊은 중첩 (3단계 이상) | 가독성 | Early return 사용 |
| 숨겨진 부작용 | 예측 가능성 | 부작용을 명시적으로 |
| 순환 의존성 | 결합도 | 이벤트나 역전 사용 |
| 섞인 추상화 레벨 | 응집도 | 레이어 분리 |

## 기억하세요

이 원칙들은 **가이드라인이지 절대적인 규칙이 아닙니다**. 컨텍스트가 중요합니다:
- 때로는 실용성이 순수성을 이깁니다
- 레거시 코드 통합은 타협을 요구할 수 있습니다
- 성능이 중요한 코드는 컨벤션을 깰 수 있습니다
- 빠른 프로토타입은 완벽한 아키텍처가 필요 없습니다

**하지만 항상 언제 깨고 있는지, 왜 깨는지는 알아야 합니다.**

## 실전 적용 팁

### 작은 것부터 시작
- 한 번에 하나의 원칙에 집중하세요
- 전체 코드베이스가 아닌 작은 모듈부터 개선하세요
- 팀과 함께 한 가지 원칙을 합의하고 적용하세요

### 리뷰에서 활용
- 리뷰 코멘트에 구체적인 원칙 언급하기
- 예시: "이 함수는 응집도가 낮습니다. 데이터 fetching과 UI 로직을 분리하면 어떨까요?"
- 좋은 예시와 나쁜 예시를 들어 설명하기

### 팀 규칙으로 정착
- 주간 회의에서 한 가지 원칙 리뷰하기
- 실제 코드 예시를 가지고 토론하기
- 팀 컨벤션 문서에 핵심 원칙 포함하기

## 더 깊이 알고 싶다면

각 원칙의 레퍼런스 파일은:
- 구체적인 Good/Bad 예시
- 실전 체크리스트
- 리팩토링 전략
- 일반적인 안티패턴

을 포함하고 있습니다. 시간을 내서 천천히 읽어보세요.
